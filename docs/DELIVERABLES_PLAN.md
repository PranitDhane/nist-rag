# Deliverables Plan — NIST AI RMF Agentic RAG

> **For Claude Code:** read `CLAUDE.md` first; its working rules apply. This file is the specification for the **final phase**: packaging the finished system so a reviewer can **run it in minutes and understand it in ten**. Work stage by stage (Section 7). Each stage has: **Purpose → Input → Output → Steps → Done when → Checkpoint**. Questions in Section 10 must be asked **at the stage named**, never answered by assumption.

**What the assignment requires:**

| Deliverable | Required content |

  - a fresh-clone acceptance test;
  - the GitHub repository and the zip export;
  - a final requirements checklist.
- **Out of scope:** new features or behaviour changes. If writing the docs reveals a bug, **report it**; fixing it is a separate, approved task.

## 3. Rules for this phase

1. **No hand-typed numbers.** Every metric in README, DESIGN or RESULTS (Hit@5, MRR, thresholds, rates, latencies, token use, memory) comes from the evaluation report files through a generator script (Stage D3). If a number isn't in a report, it doesn't go in the docs.
2. **Every command in the README must be run** in the fresh-clone acceptance test (Stage D7). An untested command is a bug.
3. **The README states trade-offs honestly**, including the ones the user chose deliberately (Section 5).
4. **No secrets anywhere**, including git history (Stage D2).
5. **The docs describe the system as built.** If the docs and the code disagree, the code is the truth, and the mismatch is reported to the user.

## 5. Content specifications

### 5.1 `README.md` (in this order)

1. **Title and summary:** 3–4 sentences on what it does and the core stack.
2. **Quickstart:** about 6 commands from clone to the first answer. The time per step is filled in from the acceptance test.
3. **Requirements:** Python version (confirmed in Q1), OS notes, disk and RAM for models, internet needed once (documents, Hugging Face models, Groq).
4. **Installation:** venv, `pip install -r requirements.txt`, the PyTorch download-size note, optional Tesseract (and what changes without it).
5. **Configuration:** `.env` from `.env.example`. A table of every variable: `GROQ_API_KEY` (required), the model IDs, host/port, the LangSmith variables (optional, with a note about what gets sent).
6. **Downloading and processing the documents:** `make build` and what it does step by step, `--from-dir` for offline PDFs, rebuild commands, approximate times. **A table pairing each `make` target with its Python command, for systems without `make`.**
7. **Running the application:** `make serve`; the endpoints `/chat` and `/chat/stream`; request and response fields; how to continue a conversation with `thread_id`; `debug=true`.
8. **Example questions:**
   - from `eval/e2e_cases.yaml`, with the **assignment's own examples first** (S1 and conversation C1);
   - curl examples, including a 3-turn conversation and one streaming call;
   - one example each of an insufficient answer (with `related_sections`) and an out-of-scope reply.
9. **How it works (short):** the main and RAG graph diagrams from `docs/graph.md` and a 6–8 line walk through a request; **link to `DESIGN.md`**.
10. **Important design decisions:** a compact table of about 10 rows (decision, choice, one-line reason), each linking to its section of `DESIGN.md`.
11. **Results:** a short summary generated from `docs/RESULTS.md` (retrieval comparison, end-to-end highlights, link-check pass rate), with a link to the full file.
12. **Known limitations:** collected from every plan's README notes and the reports (Section 5.3).
13. **What I'd do with more time:** 4–6 bullets (approved in Q10).
14. **Project structure:** a short folder map.
15. **Testing and evaluation:** `make test`, the evaluation targets, what needs a key or a running server, token and time costs.
16. **Troubleshooting:** Groq 429s and the tokens-per-minute limit; first-run model downloads; `make` on Windows; Tesseract missing; an unknown `thread_id` after a restart (behaviour from API Q12).
17. **Development process:** one paragraph and a link to `docs/process/`. Whether and how to mention AI-assisted development is **Q5**.

### 5.2 `DESIGN.md`

The assignment says the design explanation "does not need to be extensive", so the length is approved in **Q4**. Structure:
1. **Design at a glance:** one table of the key decisions and their reasons.
2. **The assignment's six points**, each with: the problem, the decision, the alternatives considered, the trade-off, and the evidence (a number from `RESULTS.md` or a test). Source material: `docs/process/PROBLEMS_AND_SOLUTIONS.md`.
   1. Document splitting: PDF as the source of truth, page-wise Markdown, the page map, section-first splitting, table-aware chunks, 250–350 tokens, the 512-token limit, footnotes and figures as their own chunks.
   2. Embedding model and vector store: bge-small, normalization, cosine distance, Chroma, the index manifest, BM25 alongside.
   3. How retrieval works: hybrid search with weighted RRF, the query prefix, the cross-encoder reranker, top 5 plus siblings, best-first order, the threshold chosen from evaluation data.
   4. LangGraph workflow: the main graph and RAG subgraph diagrams, the nodes, no loops, state design, error handling.
   5. Insufficient or irrelevant context: the out-of-scope route, the relevance gate, the strict partial-answer rule, Case D, related sections, reason codes, no retries.
   6. Conversational context: `thread_id`, the checkpointer, the 2-turn routing window, standalone-query rewriting, no history in generation, the history rules.
3. **Grounding and citations:** the prompt's five sections, sentence-level citations, the fixer policy, the honest note on uncited sentences, the link check.
4. **Free-tier constraints:** tokens per minute as the binding limit, and how the design respects it (with measured numbers).
5. **Evaluation approach:** what each evaluation measures, and its limitations.

### 5.3 Known limitations (to collect, then verify against reports)

At minimum, check these and keep the ones that are true of the built system:
- Figure 2 OCR fails (curved text); figure text depends on Tesseract.
- Footnote markers aren't linked to sentences.
- The References appendix isn't retrievable.
- The reranker's 512-token input limit.
- The threshold is tuned on a small set.
- `EnsembleRetriever` hides fusion scores (diagnostic mode exists).
- In-memory history is lost on restart, and memory grows with conversation length (measured).
- Uncited sentences and over-length answers are kept with a warning (measured rates).
- Partly answerable questions are refused entirely (deliberate).
- "Top 5 related sections" may include loosely related ones.
- English answers only.
- Free-tier throughput: about 2 answers per minute (measured).
- The local support score isn't an independent judge.
- Cleaning rules are tuned to these two documents.

## 6. Makefile specification

Targets (all assume an **activated venv**; `PYTHON ?= python` can be overridden):

| Target | Runs |
|---|---|
| `help` | Lists the targets (the default) |
| `install` | `$(PYTHON) -m pip install -r requirements.txt` |
| `download` | `$(PYTHON) -m ingest --only-stage 2` (or the acquire step as built) |
| `ingest` | `$(PYTHON) -m ingest` |
| `chunk` | `$(PYTHON) -m chunking` |
| `index` | `$(PYTHON) -m indexing` |
| `build` | `ingest` → `chunk` → `index`, stopping at the first failure |
| `rebuild` | the same with `--rebuild` on each |
| `serve` | `uvicorn app.main:app --host $(HOST) --port $(PORT)` |
| `test` | `$(PYTHON) -m pytest -q` |
| `eval-routing`, `eval-retrieval`, `e2e` | the evaluation scripts (`e2e` needs `BASE_URL` and a running server) |
| `results` | `$(PYTHON) docs/build_results.py` |
| `clean` | removes `data/processed`, `data/chroma`, `data/index` (**never** `data/raw` without `clean-all`) |
| `clean-all` | also removes `data/raw` (asks for confirmation) |

Each target prints what it's about to run. The exact command flags must match the built CLIs; verify, don't assume.

## 7. Stages

### Stage D0 — Prerequisites

1. Confirm with the user that the end-to-end evaluation is complete, and that its report and every earlier report exist. List the report files found.
2. Ask the user to approve updating the "Current phase" line in `CLAUDE.md`.
3. **Ask Q1:** confirm the final Python version (it may already be recorded in `PROGRESS.md` from ingestion).

**Checkpoint:** the report inventory.

### Stage D1 — Makefile

**Steps**
1. Write the Makefile per Section 6, matching the real CLI flags.
2. Test from a state where `data/processed`, `data/chroma` and `data/index` are deleted (`make clean`), then run `make build`. Record the time of each step.
3. Test `make test` and `make serve` (start it, call `/chat` once, stop it).

**Done when:** every target works, and the timings are recorded.

**Checkpoint:** the output of `make help` and the timing table.

### Stage D2 — Repository hygiene

**Steps**
1. `.gitignore`: `data/`, `.venv/`, `.env`, caches, model caches, generated reports per Q8.
2. `.env.example`: every variable, with comments and empty secrets.
3. `requirements.txt`: exact pins; `pip check` passes; report any unused packages (**ask before removing**).
4. Remove dead code and leftovers: `rag_stub` must already be gone; look for temporary hooks, commented-out blocks and debug prints. **List them and ask before deleting** anything that isn't obviously dead.
5. **Ask Q2:** add a linter or formatter (e.g., `ruff`)? If yes, run it, show the changes, and make sure the tests still pass.
6. **Secret scan:** search the working tree **and the full git history** for API-key patterns (`gsk_`, `lsv2_`, `sk-`), `.env` files, and tokens. If anything is found in history, **stop and tell the user** (rewriting history is their decision).
7. **Ask Q3:** licence (none, or e.g. MIT). The NIST PDFs are not committed; they're downloaded.

**Done when:** all checks are clean, or the findings are reported.

**Checkpoint:** the hygiene report.

### Stage D3 — Generated results (`docs/RESULTS.md`)

**Steps**
1. `docs/build_results.py` reads the report files: retrieval evaluation, routing evaluation, generation behaviour and usage, link check, insufficient-path report, integration (memory, per-path), and end-to-end. It writes `docs/RESULTS.md` with one section per report: the key table, the run date, and the config/prompt versions.
2. It also writes a short summary block into `README.md`, between the markers `<!-- RESULTS:START -->` and `<!-- RESULTS:END -->`, so the README numbers always match the reports.
3. **Ask Q8:** whether the raw report JSON files are committed (the evidence trail) or git-ignored (with only `RESULTS.md` committed).
4. A test: running the script twice gives identical output; a missing report produces a clear "not run" note instead of a crash.

**Done when:** `make results` produces `docs/RESULTS.md`.

**Checkpoint:** show `docs/RESULTS.md`.

### Stage D4 — `DESIGN.md`

**Steps**
1. **Ask Q4:** target length (proposal: about 4–6 pages; each of the six points in under about 250 words, plus the at-a-glance table).
2. Write it per Section 5.2, drawing on `PROBLEMS_AND_SOLUTIONS.md`, the plans' decision tables, `docs/graph.md` and `RESULTS.md`. Every claim of evidence links to a result or a test.
3. Cross-check against the code: every decision described must match the built system (Section 3, rule 5). List any mismatches for the user.

**Done when:** the user approves the draft.

**Checkpoint:** show the full `DESIGN.md`.

### Stage D5 — `README.md`

**Steps**
1. **Ask Q5** (how, or whether, to mention AI-assisted development), **Q9** (project title) and **Q10** (the "more time" list; proposal below).
2. Write it per Section 5.1, keeping the generated results block between its markers.
3. Proposed "What I'd do with more time" list, for the user to edit:
   - an LLM-as-judge evaluation on a larger set, alongside the local checks;
   - a query-rewrite retry, measured against the false-negative rate from the retrieval evaluation;
   - persistent conversation history (SQLite checkpointer) and history trimming;
   - a simple chat UI over the existing SSE endpoint;
   - re-tuning the threshold and weights on a larger, independently labelled set;
   - better figure extraction (vision model) for Figure 2-type images.
4. **Ask Q11:** also export a Postman collection (`docs/postman_collection.json`) with the example requests?

**Done when:** the user approves the draft.

**Checkpoint:** show the full `README.md`.

### Stage D6 — Process documents

**Steps**
1. Move all plan files into `docs/process/plans/`, and `PROGRESS.md` and `PROBLEMS_AND_SOLUTIONS.md` into `docs/process/`.
2. **Update every reference**: in `CLAUDE.md` (Section 2's paths), in the plans' cross-references, and in the README and DESIGN links. Search for the old paths and confirm zero remaining.
3. **Ask Q6:** `CLAUDE.md` stays at the repository root (recommended: Claude Code loads it from there) or moves to `docs/process/`.
4. Write `docs/process/README.md`: a short explanation of what these documents are (the design plans per phase, the decision log, the problem/solution record) and how they were used during development.

**Done when:** no broken references remain (search and link check).

**Checkpoint:** show the new `docs/` tree and the reference-check result.

### Stage D7 — Fresh-clone acceptance test

**Purpose:** prove the README works for someone who has never seen the project.

**Steps**
1. In a **new, empty folder** (and a new venv), follow the README **literally**: clone (or copy the committed files only), create the venv, install, create `.env` with the key, `make build`, `make test`, `make serve`.
2. Run the README's own examples against the server: S1, conversation C1 (all 3 turns), S7 (insufficient), S9 (out of scope), and one streaming call.
3. Record: the time per step, any README step that failed or was unclear (**fix the README, not the code**, unless it's a real bug, in which case report it), and the final disk use of `data/`.
4. Put the measured times into the README's Quickstart (by script or by carefully copying from the recorded output).

**Done when:** a clean run passes every step with no undocumented action needed.

**Checkpoint:** the acceptance log.

### Stage D8 — Packaging and final checklist

**Steps**
1. **Ask Q7:** the GitHub repository name and visibility.
2. Push to GitHub only after the Stage D2 secret scan is clean, **with the user's go-ahead**.
3. **Zip export** with `git archive` from the final commit, so it contains exactly the committed files: no `data/`, `.venv/` or `.env`. List the zip's contents, check its size, and confirm none of those are inside.
4. **Unzip test:** unzip into a new folder and repeat a short version of Stage D7 (install, build, test, one `/chat` call).
5. **Final checklist:** walk through the table in Section 1, plus the assignment's "What We Evaluate" list (understanding of RAG, LangGraph implementation, retrieval strategy, handling of insufficient or irrelevant context, source attribution, conversation handling, code quality, technical reasoning and trade-offs). For each, point to where it's shown (a file, a section or a result). Save it as `docs/process/SUBMISSION_CHECKLIST.md`.

**Done when:** the checklist has every item covered, and the user has the repo link and the zip.

**Checkpoint:** show the checklist and the zip contents listing.

## 8. Testing rules

- `make test` must pass on a fresh clone before packaging.
- Documentation changes never change behaviour. Any code change found necessary is reported and handled separately.
- Generated sections (results) are never edited by hand.

## 9. Definition of done (the whole project)

- A fresh clone, following only the README, reaches a cited answer and a working 3-turn conversation.
- README and DESIGN cover every item the assignment requires, with numbers generated from reports.
- No secrets in the tree or history; the zip contains only committed files.
- `docs/process/SUBMISSION_CHECKLIST.md` maps every evaluation criterion to evidence.
