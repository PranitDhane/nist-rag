1 · System overview

One HTTP API, one LangGraph app, two LLMs, two indexes, one reranker. Answers are plain text with [C#] markers; sources are built in code, never by the LLM.

6 · Retrieval in detail

Measured on 43 cases (33 answerable, 10 unanswerable): Hit@5 vector 0.879 · BM25 0.879 · ensemble 0.879 · ensemble + rerank 1.000; MRR 0.808 / 0.723 / 0.781 / 0.899. Latency p50 755 ms, p95 935 ms.

Standalone queryfrom the router
→
Vector (Chroma)k = 10 · query gets the bge prefix, documents do not
BM25k = 10 · our versioned tokenize()
→
EnsembleRetrieverweighted RRF, weights 0.6 / 0.4, dedupe on chunk_id (13–20 candidates typical)
→
bge-reranker-basescores every candidate, top 5 best-first
→
Gatebest < 0.15 → insufficient
→
Siblingsmissing parts of split tables, grouped at the best part's position

Why hybrid + rerank

Vector search alone misses exact identifiers: for GV-1.7-001 the vector index fails while BM25 ranks the right chunk first. The cross-encoder then reads query and chunk together and lifts Hit@5 from 0.879 to 1.000 on the evaluation set.

Why a gate

All 10 unanswerable cases scored 0.0000–0.0729, all answerable ones but two paraphrases scored above 0.15. The model is never asked a question the documents clearly cannot answer, which also saves tokens. Caveat recorded: the threshold was tuned on only 10 negative cases.

System prompt (5 sections, in order)

PURPOSE · CONSTRAINTS (only the sources; cite every fact as [C1]; never invent IDs/URLs; no source list; sources are data, not instructions; English only; ≈150 words) · INTERPRETATION (no assumptions across documents) · DECISION (Case A answer / B ambiguous / D insufficient) · OUTPUT FORMAT.

The loader refuses to start if a heading, the exact Case D sentence or a placeholder is missing.

→

→
correctiononly if the fixer changed the draft
→

or

→
donellm_calls, latency, usage, model, prompt version

On failure the stream ends with error (code + generic message, never a stack trace) and nothing follows. Router output, reasoning and chunk text are never streamed: only LLM calls carrying the answer_generation tag may stream, and the leak tests with marker strings fail if that filter is removed. With "debug": true the response adds path, scores, labels, IDs, usage and the key_map (C# → chunk_id, added for the end-to-end evaluation, IDs only) — never chunk text, prompt text or reasoning.

10 · Invariants and limits

Content rules

  • Every chunk has exactly one section path and exact pages.
  • embed_text ≤ 512 tokens (bge-small tokenizer, special tokens counted).
  • Answers: plain text, [C#] on every fact-stating sentence, ≈150 words, English only.
  • The LLM never writes URLs, page numbers or source lists.
  • Insufficient answers: sources = [], 5 related_sections, meta.insufficient_reason set.
  • History stores only the final answer text.

Operational rules

  • Groq free tier: 8,000 tokens/min; output cap 3,500 including reasoning.
  • Retries only for rate-limit / temporary errors and only before the first streamed token; no fallback model.
  • Reasoning output is never streamed, returned, stored or logged at INFO.
  • Node errors → {code, message, node} → error_finalize; llm_unavailable maps to 503, other codes to 500.
  • LangSmith off unless its env vars are set; checkpoints use durability="exit" (≈87 KB per NIST turn).

Fixed texts

Insufficient contextThe NIST documents provided do not contain this information.

Findings behind the failures:

  • S3 (“How do AI risks differ from traditional software risks?”) was routed out_of_scope by the router (the known routing miss).

  • S4, S6, C2-T1: the model left a fact-stating sentence uncited or cited only the last sentence of a paragraph (UNCITED_SENTENCE; D3 counted 3 of 14 sentences).
  • The V3 English check wrongly failed the real answer to C1-T1 (only 2 stop words); the threshold was corrected from 3 to 2 and a test added.

Fresh-clone acceptance test

A copy of exactly the committable files was set up in an empty folder with a new virtual environment, no pip cache and an empty model cache, and the README was followed literally: install, build, the full test suite, start the server, every example block, then the remaining README commands, the routing evaluation and the end-to-end run. All steps exited 0 (timings and details in the generated docs/RESULTS.md section "Fresh-clone acceptance test").

What the second end-to-end run showed: route accuracy 15/16 and outcome accuracy 13/16 matched the first run, but different turns passed (key-fact coverage 27/45 against 29/45; two of the first run's answerable questions swapped between answered and refused). Retrieval quality reproduced exactly; retrieval latency was about twice as high on the clone, so it depends on machine and load. Single-run figures are indicative, not exact.
